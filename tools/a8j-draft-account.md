# A8j draft — the author's own account (drafted on ALI-BLADE15 against 7d4b0ad5; NOTHING was run)

## Summary
A8j, "Enter in a form never skips its confirm". Both findings hold against the code at 7d4b0ad5.

1. **/wallet/withdraw (money).** The form has exactly one text field (the amount box renders `type=text`; radios and hidden inputs don't count) and no submit button, because ConfirmDialog forces its trigger to `type=button`. So Enter in the amount box submits `withdrawAction` with no confirm.
2. **/profile/account.** Same shape: one input beside a textarea. Enter closes the account and its wallet.
3. **A third path the findings missed.** Before the page hydrates (its scripts still loading on a slow line), the server-action form is plain progressively-enhanced HTML. The same Enter then posts the action natively, and no client listener exists yet to stop it. `withdrawAction` needs nothing a native POST lacks.

**The fix lives in one place: a new opt-in `ConfirmDialog` prop, `submitsForm`.** It has three parts, each covering a window the others cannot:

- **(a) A form guard.** `formGuard()` is exported pure, so the suite drives the same rule the dialog runs. It is a native `submit` listener on the trigger's form. It refuses every submit the dialog's own confirm did not start: it calls `preventDefault`, and it calls `stopPropagation` so React's root never sees the submit. Without the stop, react-dom 19.2.5 still marks the form pending when the same event started a transition, and the withdraw dialog's payee lookup is a server action, which Next 16 runs as a transition. It then opens the dialog by the trigger's own path (`openGuard`, then `onOpen`, then open), or does nothing where the trigger would do nothing (disabled, or already open). The confirm's own `requestSubmit()` passes because its submit event fires inside `guard.confirm(...)`.
- **(b) A hidden default submit button, disabled until the guard listens.** Before then (server markup, hydration), Chromium and Firefox stop implicit submission outright. After, Enter in any field presses it, so the guard opens the dialog in every engine, whatever the form's field count. It carries `formNoValidate`, so bad input gets the kit's toast, never the browser's bubble.
- **(c) A hidden, unnamed second text field.** WebKit (every iPhone browser) skips a disabled submit button and still submits a one-text-field form. With two text fields no engine submits.

I verified all three engines' rules from their source.

**Consumers given `submitsForm`:**
- withdraw, close-account: the two that could be bypassed;
- deposit: safe today only because it has eight text fields;
- the RG confirm (cool-off and self-exclusion): no text field today;
- the journey hub's sign-out row: no field at all.

**Gate:** new `scripts/implicit-submit.test.mts`, with an in-process red twin of 32 plants. It covers:
- **§1** the guard's behaviour on real `EventTarget` submit events;
- **§2** the server's markup, built by esbuild from the source text, rendered and read by each engine's rule, with a control showing the old form and each half of the fix alone fall short;
- **§3** structural wiring in `confirm-dialog.tsx`;
- **§4** a scope-aware syntax-tree census of every ConfirmDialog and ConfirmModal `onConfirm` in src/ (through wrapper props, failing closed):
  - every confirm that submits a form must carry `submitsForm`, and the five today are required by name;
  - no ConfirmModal may submit a form;
  - every form whose submit opens a confirm must never reach the confirm's commit, except two forms named in a ledger with their opener;
- **§5** wiring in package.json.

**Drive:** new `scripts/qa-implicit-submit.mjs`, eight cases on a local in-memory server, including two with every script held back (the pre-hydration path).

Nothing a player sees changes in words, figures or classes. The only visible behaviour change: Enter in these forms now opens the confirm. That is new on deposit, where Enter did nothing before.

## Calls for Ali (decisions the author took)
1. Pre-hydration is closed too, by server-drawn markup, which goes beyond what A8j asked. Decision: a hidden default submit button, disabled until the guard listens, stops Enter in Chromium and Firefox (most players). A hidden, unnamed second text field stops it in WebKit (every iPhone browser). Why: before the page's scripts run, a server-action form is plain HTML, so Enter posts withdrawAction or closeAccountAction natively and no client listener can stop it. I checked WebKit's source: it skips a disabled submit button and still submits a one-field form, so the finding's 'disabled default button' alone would not protect iPhones. Overrule options: (1) drop the second field and accept that an iPhone can still send a withdrawal with Enter in the seconds before the page wakes; (2) go further and add a server-side seal, where withdrawAction and closeAccountAction refuse a post that didn't come through the confirm. That touches the money actions and needs a refusal sentence in en/sw/zh.
2. Enter now opens the confirm on the deposit form too; before, Enter there did nothing, because eight text fields stop implicit submission. Decision: one rule for every form whose commit is a ConfirmDialog, 'Enter does what the button does', so deposit's safety no longer rests on its field count. Overrule: keep deposit's Enter doing nothing. That needs a guard-only variant of the prop (no default button) plus a census exemption for deposit.
3. The hub's sign-out row and the two RG confirms (break, self-exclusion) get submitsForm too, though Enter could never submit them: no text field. Decision: the census rule is the same for every dialog, 'a confirm that submits a form guards it', with no exemptions to rot. Nothing they draw or do changes. Overrule: exempt them by name in the census instead.
4. Close-account: Enter now does nothing until the phrase is typed, then opens the dialog. It used to post and come back with the 'type the phrase' error. Decision: Enter follows the trigger, which is disabled until the phrase matches. Overrule: show the old message on Enter with an incomplete phrase. That needs a toast with wording in three languages.
5. Two admin forms are exempted by name, because they save some changes directly by design: GlobalConfigForm (only a money-model change asks) and ReadingMethodForm (only the simulated feed asks). The census pins that each one asks before it saves. Overrule: make either always confirm, and its exemption goes (the census then demands the exemption be deleted).
6. A ConfirmModal may no longer be wired to submit a form (the gate fails). Such a form must use ConfirmDialog with submitsForm, because ConfirmModal has no guard. Overrule: add the same guard to ConfirmModal if a future design needs that shape.
