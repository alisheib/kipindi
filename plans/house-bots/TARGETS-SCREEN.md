## 1. What this screen is

The targeting screen is the officer's way to point ONE house account at ONE live poll, to change the timing of that pointing, and to stop it. Nothing else. An officer picks a poll, chooses a whole-second delay between 5 and 600, says whether the delay counts from the player's stake or from the moment the player's free exit closes, says whether the account answers only the first stake or every stake, writes a reason, and presses. The account then answers stakes on that poll on the engine's own terms: the side is computed (always opposite the trigger — `src/lib/server/house-bot/decide.ts:275`), the amount is computed at the reaction's due instant against locked player money (`decide.ts:375-378`), and the reaction never lands before the player's free exit closes plus `LOCK_MARGIN_MS` (`decide.ts:485-488`; the constant is derived, `src/lib/house-bot/constants.ts:517`). The officer types five things and nothing else: the poll, two numbers, two choices, and a reason (`plans/house-bots/PLAN.md:737-741`, `:757-759` "Do not restore: No human-typed side. No human-typed amount.").

**What it is NOT.** It is not a money screen: ruling 365 forbids any per-market, per-player or per-officer money figure anywhere in the console (`plans/house-bots/C7-SPEC.md:739-743`), and the built reader says the same on the row type it already ships — "⛔ No money: a target is a scope decision, not a stake (365)" (`src/lib/server/house-console-read.ts:3344`), repeated at the render site with D20's reason (`src/app/admin/desk/[id]/page.tsx:840-841`). It is not public and it is not the holder's: D19 keeps house bots out of every player surface and out of the holder's own data-rights export — the target row is "Officer ids and public poll fields only … Never in the holder's data-rights export" (`docs/HOUSE-BOTS.md:96`), the targets tab carries no Board-disclosure line (`plans/house-bots/04-amendments.md:4261`), there is no public text about targets at all (`04-amendments.md:4382`), and every alert an act sends goes to ADMIN accounts only (`src/lib/server/house-bot/alerts.ts:16-19`). It is not a report: D20 struck R1's targets register, R1's vetoes section and the R9 staff-chosen counting (`plans/house-bots/C5-D20-REPLAN.md`; the per-row strikes at `01-scenario-register.md:3717`, `:3740`, `:3528`, `:3831`; TGT-39 struck whole at `:3796`). The screen owes history events and COMPLIANCE audit rows, and no report output at all.

## 3. The four acts

All four share one skeleton, fixed by `04-amendments.md:4137-4143`:

```
requireHouseOwner()                                   — C12, first statement, never throws (04:4129, :4159)
validate input (validateTargetInput + reason 5–300 code points)
pressStore.insertChecking(...)                        — durable, before any lock (04:4129-4133)
SET LOCAL lock_timeout = '3s'
withLock wallet:<botUser> → withLock house:targets    — never house:control (constants.ts:42-45)
  getForUpdate / everStopped / activeForMarket / countActive   (the in-lock checks)
  the store write
  houseBotEventStore.append(kind, marketId, …, reason: <officer text>)
  pressStore.doneInTx(press.id, tx, { targetId })     — 0 rows ⇒ roll back
COMMIT
writePressAudit(press, pressAuditEntry(...))          — AFTER the locks (A19)
houseBotEventStore.setAuditId(event.id, auditId)      — only when auditId is non-null
announceRoster({ …, event: "<LITERAL TARGET_*>", eventId: event.id, actorId })
```

A refusal returns before the write and therefore before the announce, by construction. A no-change save lands and returns before the event, the audit and the announce.

**⛔ The event is appended INSIDE the locks, and `roster-actions.ts` is NOT the model for that.** `04-amendments.md:4139` step 2 is explicit for targets: "Re-read the target row `FOR UPDATE`. Run the in-lock checks. Insert, CAS-update or remove. **Append the events**, each carrying `pressId`. Move the press to DONE … Commit." The event and `pressStore.doneInTx` must commit together, because `pressAuditEntry` returns `null` for a DONE press with no matching event (`press-audit.ts:76-77`, `:84`, `:91` — each case is `press.state === "DONE" && e`) and the press is then DONE and permanently unauditable. The shipped act `roster-actions.ts` does the **opposite** — its own comment reads "── after the lock (A19): cancel, then the event, then the awaited audit, then the alert ──" (`roster-actions.ts:95`), with `houseBotEventStore.append` at `:97` and `announceRoster` at `:107`, all outside the `withLock` that closed at `:88`. A19's scan is about `audit(`, not about the event, so both files obey A19; they differ on the event's position and the target rule is 04:4139's. **Copy `roster-actions.ts` for the AUDIT/ALERT tail only** — the awaited `actAudit`, the `setAuditId` guard on a non-null id, and the unguarded `announceRoster` — and never for where the event goes.

**⛔ Every target event carries `marketId`.** Not only the ADD. `pressAuditEntry` spreads `marketId: e.marketId` into all three COMPLIANCE payloads — `house_bot.target_added` (`press-audit.ts:78`), `house_bot.target_updated` (`:85`) and `house_bot.target_removed` (`:92`) — and `isAllowedHouseAuditPayload` validates key NAMES and never values (`constants.ts:987` `Object.keys(p).every((k) => allowed.includes(k))`). So `marketId: undefined` does not refuse: the key vanishes from the payload, the row lands, and the seven-year compliance record for a timing change or a removal **cannot name the poll**. See D-75.

Five things the mapping proved that the refusal table hides:

- `casUpdate`'s `{ok:false, current}` is **ambiguous**: `current: null` means the row is gone; `current: <row>` means EITHER a stale version OR a status that is no longer ACTIVE — both failures take the same return path (`house-bot-dal.ts:4338-4340`, memory `:2984-2986`). The action must read `current.status` to choose between `STALE_VERSION`, `TARGET_REMOVED` and `TARGET_ENDED`. Mapping every `ok:false` to `STALE_VERSION` tells an officer "someone changed this" about a target that was removed, and they retry into a permanent failure.
- An **empty patch still writes**: `patchSets` returns `[]` for an all-undefined patch and the SQL still pushes `"version" = "version" + 1` and `"updatedById"` (`house-bot-dal.ts:4334-4335`; memory `:2987`). So the no-change no-op must **skip `casUpdate` entirely**, diffing against the in-lock re-read. Calling it and then suppressing the alert still bumps the version and invalidates every other officer's open form.
- The patch must carry **all four** fields every time. `casUpdate` does not re-check `delayMinSec <= delayMaxSec` against the merged row; a partial patch that crosses the stored value raises a raw 23514 `HouseBotTarget_delay_order_check` (`migration.sql:366`; the memory mirror at `house-bot-dal.ts:847` via `:2103-2105`) — a 500 with no field and no copy.
- A patch key outside the four throws a plain `Error` on both twins (`house-bot-dal.ts:1096-1104`, `:1107-1113`). Build the patch from a fixed literal, never by spreading form data.
- **`changes[].before/after` must be coerced to numbers before the event is appended.** An HTML input hands the action strings. `isChangeValue` (`constants.ts:969-974`) requires `null` or a finite `number` for every field outside `ENUM_CHANGE_FIELDS = ["timingFrom","reactTo"]` (`constants.ts:958`), so `{field:"delayMinSec", before:"10", after:"20"}` fails `isAllowedHouseAuditPayload`, `pressAuditEntry` returns `null` (`press-audit.ts:108`) and the COMPLIANCE row silently never lands. See D-78.

The success sentence is required copy, not decoration: "Target updated — applies to stakes decided from now on. Queued reactions keep the timing they were decided with." (`04:4205`). It is the only place the officer is told the edit is not retroactive.

`remove` has **no knowledge of intents** — the whole statement is a three-field update with no join (`house-bot-dal.ts:4342-4349`). "A removal with no live reaction" in its docblock is the CALLER's precondition, not a guard. An action that calls `remove` without counting first silently removes a target whose queued reactions stay PENDING and still fire.

`remove` returning `null` does not say why — missing, already REMOVED and already ENDED all return null (`:4342-4348`). The action takes `getForUpdate(targetId, tx)` **FIRST, in the same transaction** (C7 436(f), `C7-SPEC.md:1917-1918` — a review finding refuted only on that condition) and produces the three different sentences from the row it read.

### 4.5 The timing preview

**What it previews — four things, not one** (`04:4109-4124`):

1. `short` — the compact form for the table cell, e.g. "10 s → held to 5:07".
2. `sentence` — the full explanation, which always appends "Armed from {HH:MM:SS} EAT." and "Stakes placed after {HH:MM:SS} EAT aren't reacted to.", and, when `noReactZoneSec < graceMin × 60`, also "From {HH:MM:SS} EAT a stake has no free exit, so [the account] reacts {delay} s after it."
3. `held` — whether the absolute hold lifts `dueAt` above what was asked.
4. `never` — no reactable instant at or after `armedFrom`; this becomes the `TOO_LATE` refusal (`04:4190`).

**What computes it — and what does NOT.** The preview calls `effectiveTargetTiming` (`src/lib/house-bot/rules.ts:3684-3705`). Its return type is exactly `{earliestAfterStakeSec, latestAfterStakeSec, held, sentence, short, lastReactableStakeAt, armedFrom, never}` (`rules.ts:3651-3668`). Note the built signature takes one argument the amendment does not name — `opts: { botLabel?: string } = {}`, placed last "so it never shifts the sealed arguments" (`rules.ts:3691`, rationale `:3682`).

⛔ **THE ENGINE DOES NOT CALL IT. THERE ARE TWO IMPLEMENTATIONS OF THE DUE-TIME RULE AND NOTHING IN THE TREE COMPARES THEM.** Measured 2026-09-28, by grep across `src/` and `scripts/`:

- The **only** `src/` caller of `effectiveTargetTiming` is the planner's end-sweep, `src/lib/server/house-bot/planner.ts:337` — which uses it to decide `CUTOFF_PASSED`, not to time a reaction.
- The engine's actual due instant comes from its **own** function, `targetDueAt` (`src/lib/server/house-bot/decide.ts:485-488`), called at `decide.ts:348` and `trigger.ts:239`. It is millisecond arithmetic: `requestedMs = (timingFrom === "STAKE" ? placedAtMs : exitCloseAtMs) + delaySec*1000; dueMs = max(requestedMs, exitCloseAtMs + LOCK_MARGIN_MS)`.
- `effectiveTargetTiming` reaches the same rule through a **different** helper, `targetDueAfterStakeSec` (`rules.ts:3441`, used at `:3707`, `:3712`, `:3719-3720`), expressed in seconds after the stake over `holdAfterStakeSec` (`rules.ts:3433-3434`, `LOCK_MARGIN_SEC = LOCK_MARGIN_MS / 1000` at `:3414`).
- The suites test each **separately and never against each other**: `scripts/house-bot-rules.test.mts` imports `effectiveTargetTiming` (`:138`) and `targetDueAfterStakeSec` (`:161`), and pins `targetDueAfterStakeSec("STAKE", 300, 10) === 307` (`:1528`); `scripts/lib/house-bot-engine-cases.mts` pins `DE.targetDueAt(...).dueMs === 307_000` (`:474-477`, case 7.35). **The same golden row, asserted twice, in two suites, with no line comparing the two functions.** The test file never references `targetDueAt` at all.

That matters because the amendment **requires** the comparison and the tree does not have it: "It is pure, in `src/lib/house-bot/rules.ts`, with no server imports (03 trap 2). `decide.ts` and `previewHouseBotTargetAction` both use it." (`04:4101`) and "`effectiveTargetTiming` equals `decide.ts` on every golden row, including the 7 s hold" (`04:4396`), with the golden-row table headed "*Golden rows (`test:house-bot-rules` asserts `decide.ts` gives the same seconds*)" (`04:4109`). None of that is true today. This is the "explanation that is a second implementation" defect, already shipped, and the preview is about to become its second reader on a real-money console.

S3 closes it, one of two ways, and says which in its commit (D-31):

- **Preferred — one arithmetic, one owner.** `decide.ts` already imports from `@/lib/house-bot/rules` (`decide.ts:25`), so nothing prevents sharing: lift the `max(requested, exit + LOCK_MARGIN)` step into the pure helper `rules.ts` owns and have `targetDueAt` call it, leaving `targetDueAt`'s millisecond signature intact so engine case 18.6 — "the trigger times a targeted row only through `targetDueAt` (no lock-margin arithmetic of its own)" (`house-bot-engine-cases.mts:3884-3885`) — stays green.
- **Otherwise — a case that can fail.** A new `test:house-bot-rules` case that drives BOTH over the same golden rows and asserts equality: for every row of `04:4109-4124`, `targetDueAt({placedAtMs: 0, exitCloseAtMs: exit*1000, timingFrom, delaySec}).dueMs === targetDueAfterStakeSec(timingFrom, exit, delaySec) * 1000`. Its RED control is a declared mutation that changes the constant in ONE of the two (`target-duetime-drift`), which must be CAUGHT.

## 5. Every decision, with its reason and its sources

### Placement and shape

**D-1 · The Add screen is a PAGE at `/admin/desk/[id]/targets/new`, not a modal.**
*Reason:* `BY_HAND_SCREENS.targeting` is tied **by file existence** to `src/app<route>/page.tsx`, in both directions, and the module says in as many words that building it elsewhere "means moving the tie here first, in the same change" (`src/lib/house-bot/console-routes.ts:248-263`; the assertion is `scripts/house-bot-rules.test.mts:1823-1826` with a two-direction control at `:1827-1829`). N2 §8 specifies a modal (`04:4314`). **The code wins** because the modal costs a tie move for no gain, and because a 640px form with a picker, five fields and a four-part preview does not fit a 420px modal at 640 width.

**D-2 · Change and Remove ARE modals, on the Targets tab — and all three target dialogs pass `closeOnScrim={false}`.**
*Reason:* the tie names only the ADD screen; `03-design-spec.md:310` specifies kit `Modal` for "Add / Edit / Remove target" and defers the body to 04 N2 §8. Modal law for these three: `maxWidth={420}`, **`closeOnScrim={false}`**, explicit `initialFocus`, Esc closes unless pending, focus returns to the trigger, no `truncate`/`line-clamp` inside (`03-design-spec.md:313-318`).
*On `closeOnScrim` specifically:* 04 N2 §8 writes it out — "**Add / Edit target modal** (`Modal maxWidth={420} closeOnScrim={false} labelledBy={titleId}`…)" (`04:4314`) — and 04 carries a SOURCE PIN that form modals pass `false` (`04:2007`: "Source pin: form modals pass `closeOnScrim={false}`"). The `!pending && !dirty` form belongs to the Master-ON / Remove-account rows of the 03 dialog table (`03-design-spec.md:303-304`), which are different dialogs; the target row (`:310`) states no `closeOnScrim` at all. The source table ranks 04 above 03 (`PLAN.md:811`), and here 03 does not even dissent. A reason-bearing form modal that closes on a scrim click throws away the officer's typed reason on a misclick, which is also why the C12 draft exists (D-79).

**D-3 · `BY_HAND_SCREENS.targeting` flips to `true` in the SAME commit as the page file, and in no other — and that one-word flip moves TWO more things that must ride in the same commit.**
*Reason:* the existence tie refuses either alone (`console-routes.ts:262`; the line itself is `console-routes.ts:263`).
