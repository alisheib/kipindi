## Q1 · IS THE LOGIC MISSING — IS EVERY GATE ACTUALLY **WIRED**?

⭐ **YES, ALL OF IT. This half of the audit is clean, and it is asserted at the CALL SITE rather
than by the presence of a symbol** — the platform's own recorded KYC-domain lesson.

| gate | call sites, measured | verdict |
|---|---|---|
| `checkDepositLimit` (`:305`) | `wallet-service.ts:172`, inside the atomic reservation | ✅ wired |
| `checkLossLimit` (`:350`) | `market-service.ts:1020`, in `buyPositionInner` under the wallet lock | ✅ wired, **and it has exactly ONE caller** |
| `isLockedOut` (`:284`) | `market-service.ts:871` (bet) · `wallet-service.ts:144` (deposit start) · `wallet-service.ts:357` (**deposit webhook confirm**) · `bonus-service.ts:110` (bonus) · `push-service.ts:70` (push) | ✅ wired, in five places |
| `setLimits` (`:129`) | `profile/responsible-gambling/actions.ts:20` | ✅ wired |
| `selfExclude` (`:210`) / `coolOff` (`:251`) | same file, `:45` / `:57`, each destroying the session afterwards | ✅ wired |
| `getLimitUsage` (`:388`) | `profile/responsible-gambling/page.tsx:62` → `rg/limit-usage.tsx` | ✅ wired |
| `detectHarmMarkers` (`:558`) | via the sweep only | ⚠️ see **Q4** |
| `detectHarmMarkersForAllUsers` (`:587`) | `admin/compliance/page.tsx:404` — **and nowhere else** | 🔴 see **Q4** |

**Three things are worth stating because a reader would otherwise assume them:**

1. ⭐ **BOTH PRODUCTS ARE GATED BY ONE PATH.** Up & Down does not have its own bet route:
   `use-quick-bet.ts:5` imports `buyPositionAction` and `:331` calls it, so an Up & Down tap goes
   through the same `buyPosition` — the same `isLockedOut`, the same `checkLossLimit`. There is no
   second money path to forget.
2. ⭐ **THE DEPOSIT GATE IS AT BOTH ENDS.** `wallet-service.ts:357` re-checks the lockout when the
   **provider's webhook confirms**, so a push initiated before a break and landing after it cannot
   credit an excluded account. The code there also records what a real gateway means for that case
   rather than assuming the internal stub.
3. ⛔ **THE EXITS ARE DELIBERATELY NOT GATED, AND THAT IS CORRECT.** `withdraw` and
   `cashOutPosition` carry no `isLockedOut`. A player on a break must be able to take their own
   money out; blocking that would turn a self-care tool into a trap. **No finding.**

▶ **The house test — *would this pass if the gate were deleted?*** — `test:failure-reasons` §8c now
pins `checkLossLimit`'s single caller by name and fails if a second appears, so a new money path
cannot silently arrive without one.

## Q2 · IS IT WARNING ENOUGH?

🔴 **NO — AND THIS IS WHERE THE SYSTEM WAS ACTUALLY BROKEN.** Two findings, both fixed.

### `E-232` · the copy existed, in three languages, and nothing emitted it

Three rows in the failure registry had severity, channel and copy in EN/SW/ZH and **no emitter
anywhere in the application**: `self_excluded` (with `needs: ["until"]`), `break_active` and
`account_blocked`. `grep -rn '"self_excluded"' src/` returned exactly **one** hit — its own type
declaration. So the betting gate returned no machine `reason` at all and fell through to
`errSuspended`.

⛔ **AND THE PHRASE TEST THAT WAS SUPPOSED TO CATCH IT COULD NEVER HAVE WORKED ON TWO OF THE THREE
ROUTES.** It matched `/self-exclusion|cooling-off/i`; the betting gate said *"Locked until
27/08/2026, 19:41:00."* and the account-status branch said *"self-excluded"* and *"cool-off"* —
**the pattern matches none of those.** Only the deposit gate happened to word its English sentence
in a way that matched, so its localisation was luck.

⭐⭐ **AND THE SHARPEST PART, WHICH ONLY MEASURING THE AUTH PATH SHOWED.** `auth-service.ts:110,
827, 959` **refuse login outright for `SELF_EXCLUDED`** — so a self-excluded player can never reach
a bet card. Login does **not** refuse `COOLED_OFF`. **So the one RG lockout a player can actually
hit while signed in is the COOLING-OFF one, and there was no `cooling_off` row at all.** The copy
that existed covered a state nobody can be in; the state they can be in fell to *"try again
shortly"*.

**Fixed:** a `cooling_off` row with its own copy in three languages, both gates emitting
`self_excluded` / `cooling_off` with the end date as `detail.until`, `account_blocked` emitted from
the status-divergence branch, `formatDateTime` (the admin-configured platform timezone) instead of
`toLocaleString("en-GB")`, and the phrase test **deleted** per `error-copy.ts` §7.

### `E-234` · the reason was computed and then guaranteed unread

Found by driving E-232's fix rather than trusting it. `conviction-dial.tsx` passed the reason copy
into the result modal as `error` while also setting `title`, and the modal renders `title ?? error`
— so `error` could never be reached. The subtitle beneath it was the constant
`t.common.stakeHasntMoved`.

⛔ **So every refusal that card can produce showed the same two lines** — the stake-bounds copy that
closed `RULES.md` §2.3, the daily-loss modal the LCCP requires, the cooling-off sentence, all of it
assembled and dropped one variable from the screen. ⚠️ And that constant is itself a claim
`failure-reasons.ts` §C4 says we cannot always support.

**Fixed:** the subtitle renders the reason, with the constant surviving only as the fallback for a
refusal that arrives with no reason at all.

### What the player is told now, measured on production

`qa:rg-refused` against `4b65529d`, on a fleet account put on a **real 1-hour cooling-off through
the real form** (`status=COOLED_OFF`, confirmed on the row, two-step confirmation asserted):

| cell | modal names the break | says when it lifts | text inside its box | box in viewport |
|---|---|---|---|---|
| en @ 360 · 393 · 768 · 1024 · 1280 | ✅ | ✅ | ✅ | ✅ |
| sw @ 360 · 393 · 1280 | ✅ | ✅ | ✅ | ✅ |
| zh @ 360 | ✅ | ✅ | ✅ | ✅ |

⚠️ **SIX CELLS WERE NOT DRIVEN AND ARE NOT SCORED: sw/zh at 768 and 1024, and zh at 393/1280.** The
stake input would not accept a value in those runs — measured enabled, not read-only, holding its
`1,000` default — so this is an instrument timing problem I did not isolate, not a product defect.
⭐ **The probe REFUSES to score a cell it did not drive**, which is the property that matters: an
earlier version of this same leg passed *"the refusal is not the generic line"* on a page that
carried no refusal at all, because an absence satisfies a negative assertion.
▶ **Ali's two mandatory cells — 360 and ZH — are both covered and green.**

### ⚠️ AND ONE THING NO DESIGN CAN ASSUME TODAY

`/api/health` reports `sms.provider: "console"`. **No real SMS has ever left this platform**, so any
RG design that relies on reaching a player by SMS is fiction. ⭐ Measured separately for deposits
(`E-231`): **34 of 38** failed deposits DID get an in-app `Notification` within 10 minutes, so the
in-app channel works — the SMS one does not exist.

## Q3 · IS IT CONVENIENT WITH THE THEME UI KIT?

⭐ **YES, and it uses the kit properly rather than hand-rolling** — which is the standing rule, and
`docs/DESIGN_AUTHORITY.md` is its one door.

- `rg-confirm-submit.tsx` is a **shared** two-step confirmation wrapping the kit's `ConfirmDialog`,
  used by both self-exclusion and cooling-off. It consolidated two identical scaffolds into one
  primitive. **Asserted live: the confirmation really does stand in front of the break** — a
  misclick cannot lock a player out.
- the break-length control is the kit's `Select` (an APG select-only combobox). ⛔ **That is worth
  knowing before writing any probe against this page:** it is not a native `<select>`, so
  `selectOption` and `input[type=radio]` find nothing. This is `E-225`'s lesson and it cost this
  session a run.
- `limit-usage.tsx` reads **the same quantity the gates enforce** (`getLimitUsage`), so the meter
  cannot disagree with the refusal.
- the refusal modal is `OperationResultModal`, the same primitive the cash-out and Up & Down
  surfaces use.
- ⛔ **AND THE ADMIN NAVS SIGNALLED THE CURRENT PAGE BY COLOUR ALONE** — no `aria-current` — which
  is a11y debt found while probing this area and fixed in `E-229`'s commit. WCAG 1.4.1 / 2.4.8.

🔴 **ONE REAL DEFECT IN A COMPONENT, AND IT BELONGS TO `E-226`.** `reality-check.tsx` is
`"use client"` and calls `SUPPORT_PHONE()` from `@/lib/support-config`, whose `cfg` is
`globalThis.__50PICK_SUPPORT_CONFIG` **initialised from `DEFAULTS` in the browser**
(`support-config.ts:40`). It can therefore never see an operator-saved value — the helpline in the
reality-check prompt is hard-coded by construction. ⛔ **Not fixed here: it is one of E-226's four
recorded traps and fixing it means splitting that module so a client bundle does not drag Prisma
in.** Recorded as confirmed evidence for E-226 rather than duplicated as a new finding.

## 🔴 Q1, ANSWERED AGAIN AFTER DRIVING IT: THE LOGIC **WAS** MISSING, AND IT WAS THE END OF THE BREAK

⛔ **`E-238`. Every gate was wired — and a cooling-off break had no END.** `coolOff` sets
`User.status = "COOLED_OFF"` and **nothing anywhere ever clears it**, so the moment the timer
passed the two records diverged and the account-status branch in `buyPosition` refused every bet
for ever. **The platform's shortest, gentlest self-care option — one hour — was permanent.**

⭐ **FOUND BY ASKING A HOUSEKEEPING QUESTION, NOT BY READING THE CODE:** *did I just brick a fleet
account by cooling it off for a test?* The grep that answered it found the defect.

**Measured on production before the fix** (`qa:rg-expired`): the break ended at 18:14:30Z; at
18:22:29Z the player could still sign in, still see TZS 199,480, and a real 2,000 bet was refused
with *"Your account can't place bets at the moment. Contact support and we'll explain why."* — 0
positions. The 24-hour and one-week options behave identically.

🔴 **AND THE SELF-EXCLUSION HALF IS WORSE, IS FILED, AND NEEDS ALI:** `SELF_EXCLUDED` is refused at
**LOGIN**, so a player who picks the **24-hour** self-exclusion the form offers **cannot sign in to
discover that it never ended.** ⛔ The page shows a `ONE WAY` chip beside a form offering 24h / 1w /
1m / 6m / permanent. **Either the periods mean something or the chip does.** The bet path is fixed
for both statuses; the login gate is untouched.

✅ **The fix is read-only:** the timer is the source of truth for whether a break is over, and a
break status with **no timer at all** still blocks — because that is the genuine divergence the
branch was written for. See the register row for why restoring the status would have needed a
migration and could have upgraded a `PENDING_KYC` account.

## Q4 · FULLY INTEGRATED? — `detectHarmMarkersForAllUsers`

🔴 **NO. IT HAS NO RUNNER, AND THAT IS E-227's SHAPE AGAIN.**

`grep` over `src/instrumentation.ts`, `src/lib/server/lifecycle.ts` and `.github/workflows/`:
**no match**. The only three workflows in the repo are `ci.yml`, `backup-nightly.yml` and
`cert-expiry.yml`. The sweep is called from exactly **one** place —
`admin/compliance/page.tsx:404` — which means:

⛔ **HARM MARKERS ARE COMPUTED ONLY WHEN AN OFFICER OPENS THE COMPLIANCE PAGE.** Nothing is
scheduled, nothing is alerted, nothing is emailed, and nobody is notified. For a licensed operator,
*"we detect harm markers when someone looks"* is materially different from *"we monitor"*.

⚠️ **AND IT IS NOT SAFE TO SCHEDULE AS WRITTEN.** `detectHarmMarkersForAllUsers` does
`db.user.list()` — **every user, no cap, no cache** — and runs `detectHarmMarkers` per user in
batches of 10, on a **page render**. At 102 users that is 11 batches per page view; it grows
linearly with the roster for ever.

▶ **THE FIX IS TWO PARTS AND THE ORDER MATTERS:**
1. give the sweep a **bounded** query (last-N-days of activity, or a paged cursor) so it can run on
   a schedule without scanning the whole user table;
2. **then** schedule it — a twice-daily GitHub workflow, the shape `cert-expiry.yml` already proves,
   or the leader-lease lifecycle so it runs ONCE across containers.
⛔ **Scheduling it first would put an unbounded per-user scan on a cron.** Filed as **`E-235`**;
not built here, because it is a compliance control and it needs its own RED proof and a live run
before anyone calls it done — which is the whole lesson of E-227.

## TWO MORE LIMITS, MEASURED WHILE ANSWERING Q1 — AND ONE OF THEM MAKES A REPORT FALSE

⛔ **Both are filed as `E-235`, not fixed here.** One is a compliance-report claim and the other is
a dead column; neither is a change to make in the same pass as the copy fixes above.

### 🔴 `sessionTimeLimitMin` — SETTABLE, REPORTED AS A LIMIT, ENFORCED NOWHERE

The player can set it (`profile/responsible-gambling/page.tsx:149` → `actions.ts:25` → `setLimits`).
An operator sees it on the player page (`admin/players/[id]/page.tsx:596`). **And
`reports/catalogue.ts:858` counts `sessionTimeLimitMin !== null` toward `withAnyLimit` in
`buildRgEngagement` — the report whose own header reads *"RESPONSIBLE-GAMBLING ENGAGEMENT (internal
· RG audit)"* — and prints it per player as `sessionMin`.**

⛔ **AND NO GATE ANYWHERE ENFORCES IT.** `grep -rn sessionTimeLimitMin src/` returns the form, the
action, the DAL, the admin display and the report. **Not one refusal reads it.** A player can set a
30-minute session limit, play for six hours, and the RG audit report will list them as a player who
has set a limit.

⭐ **That is the defect this campaign was built to find: a report that states a control the product
does not keep** — the same shape as the compliance card that showed a hardcoded green tick for
backups that did not exist. **The report is not merely incomplete, it is wrong**, and it is the
document a Board reviewer reads.

▶ **Two honest remedies, and the choice is the owner's:** enforce it (a session clock the bet path
consults, which the reality check already tracks per tab and would have to move server-side), or
**stop counting it as a limit in the report and say on the form that it drives the reality-check
prompt only.** ⛔ The one thing that must not continue is the report claiming it.

### ⚠️ `weeklyLossLimit` — A SCHEMA COLUMN WITH NO CODE AT ALL

`grep -rn weeklyLossLimit src/` returns **nothing**. It exists in `prisma/schema.prisma:705` and
nowhere in the application: the player cannot set it, no gate reads it, no report prints it.
⭐ **Less serious than the row above** — an absent feature, not a false claim — but it is a column
on a compliance table that reads as a control and is not one. Either build it or drop it under the
expand→contract rule.
