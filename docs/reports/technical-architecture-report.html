Engineered for concurrent real-money load

The platform is built on the assumption that many players act on the same market in the same instant, and that the money must be exactly right under that pressure rather than merely right most of the time.

TABLE 4 — How that behaviour is achieved
PropertyHow it behaves
Contention controlAdvisory locks held by the database and keyed to the wallet or market, so they are honoured across every instance rather than within one. Competing requests are ordered, not collided.

Why server rendering matters on a pari-mutuel platform

Every page that shows money, and every action that moves it, is produced on the server. A player's browser receives finished output; it is never the authority on a balance, a stake limit, a market's status or a payout. An altered request from a modified browser reaches the same server-side rule as an unaltered one and is refused by it.

The same principle governs the administration console. A member of staff whose role does not permit an action is prevented from taking it by a check that runs on the server for that specific action, not by hiding the button. A control that is not shown and a control that is not permitted are two different things, and the platform enforces the second.

One interface, three languages

The platform is delivered in English, Swahili and Chinese. Interface text is held in a single dictionary of 1,918 keys per language rather than written into individual screens, and an automated check refuses any change that leaves the three languages out of step. A player's language governs every screen, notification and email they receive, not only the page they chose it on.

Design consistency is enforced, not encouraged

Typography, spacing, colour and component usage are held to a closed set of tokens. Automated checks reject a change that introduces a value outside that set, so the interface cannot drift screen by screen into inconsistency as it grows. The same checks confirm that each page declares its width from the shared scale and that no page duplicates a structural landmark, which is what keeps the platform navigable on a screen reader.

Note — §02

Mobile first. The platform is built for the handset first and verified at three widths in all three languages before any interface change is released. Tanzanian players reach 50pick predominantly by phone, and the narrow layout is the one that is designed rather than the one that is inherited.

Transport security

The platform is served over HTTPS only. Strict Transport Security is declared with a two-year maximum age, applied to every subdomain, and submitted to the browser preload list — so a browser that has never visited 50pick.tz will still refuse to make an unencrypted first request. Connections between the application and its database are encrypted with TLS 1.3.

HSTSmax-age=63072000; includeSubDomains; preload
Database transportTLS 1.3

Deployment

A release is produced from a commit in the source repository, built into an immutable container image and started only after its database migrations have applied successfully. Nothing is edited in place on a running server, and no change reaches production without passing through the automated checks described in Section 07.

Separation of credentials

Credentials exist only in the deployment environment and never in source code. The document store and the backup store use different credentials, so a key that reached one would not open the other. Application errors are reported to a monitoring service that is configured to receive diagnostic context, not player records.

Schema change control

The schema is versioned. Each change is a numbered, immutable migration held in the source repository, reviewed before merge and applied automatically when the release that needs it starts. Migrations move forward only and none is edited after it has been applied, so the sequence of 62 is a complete, dated history of how the data model reached its present state.

How money is written

A player's balance is a recorded liability, not a running total that is simply adjusted. Every stake, payout, refund, deposit and withdrawal is written twice: once against the wallet balance and once as a balanced set of double-entry ledger postings. The two are reconciled against each other continuously, so a balance that disagrees with its own history is detected rather than carried forward.

Each of those writes happens inside a single database transaction. A transaction either completes in full or leaves no trace, which is what makes a partial settlement impossible rather than merely unlikely.

Preventing two things happening at once

Where two operations could touch the same money at once — two stakes on one market, a settlement running while a player cashes out — the platform takes a database-level advisory lock keyed to that wallet or market. The lock is held by the database, so it is honoured across every application instance rather than only within one. Requests arriving while it is held are queued and served in order: load presents as a short wait, never as a lost or duplicated transaction.

Long-lived state does not live in the server

Application instances hold nothing that matters. Sessions are carried in signed cookies and validated against the database; counters and locks live in Redis and PostgreSQL. An instance can therefore be replaced, restarted or added at any moment without interrupting a player mid-action, and without any single machine becoming irreplaceable.

Scheduled work runs exactly once

Some work is time-driven rather than player-driven: settling a market when its objection window closes, reconciling a payment the network has confirmed, closing an expired round. With several instances running, such a task must not be performed more than once.

The platform elects a single instance to hold a time-limited lease. Only the leaseholder performs scheduled money work, and the lease expires by itself, so if that instance stops, another takes over without intervention and without any risk of both acting at once.

Capacity

Database connections are pooled with a ceiling of 40 per instance, and requests that would exceed the ceiling wait in an orderly queue rather than failing. The design decision throughout is that pressure should present as latency, never as an error shown to a player and never as a transaction in an uncertain state.

Health reporting

An internal health endpoint reports the live state of every dependency and which instance holds the scheduling lease, so a failure is visible immediately rather than discovered through a player complaint. Section 12 sets out what it covers.

Why a typed language was chosen

TypeScript checks the shape of every value before the code runs. A payout calculated in shillings cannot be passed where a percentage is expected; a market that may not have been settled cannot be treated as though it certainly has. These are not warnings — the build fails and the release does not proceed.

The practical consequence for a pari-mutuel platform is that a whole class of arithmetic and null-value defects is eliminated before any code is executed, rather than discovered by a player whose balance is wrong.

One definition of the money rules

The arithmetic that decides a payout is written once, in a single module, and imported by both the server that settles a market and the screen that shows a player what they stand to win. It is not possible for the figure quoted before a stake and the figure paid after it to be produced by two different pieces of code, because there is only one.

Validation at the boundary

Every value that enters the platform from outside — a form submission, a payment notification, an administrative action — is parsed against an explicit schema before it is used. Anything that does not match the declared shape is rejected at the boundary with a stated reason, rather than being allowed part-way in and failing later somewhere less obvious.

Development & quality assurance
07

DEVELOPMENT & QUALITY ASSURANCE

Continuous delivery, with every change gated by an automated suite that includes tests written specifically to attack the platform's own safety checks.

How a change reaches players

  1. Written and reviewed. Every change is made against the source repository on GitHub and reviewed before it is merged.
  2. Checked automatically. Continuous integration runs on every commit: type checking, the test suites, interface-consistency checks, translation parity and file encoding.
  3. Verified in a browser. Browser tests drive the real application the way a player would, at three screen widths and in all three languages.
  4. Released. A passing commit is built into an immutable image, its database migrations applied, and the instance started only if they succeeded.
  5. Confirmed live. The release is exercised against the running platform before the change is considered delivered.
TABLE 10 — The automated gate
CheckCountWhat it protects
Automated test suites243Money conservation, settlement arithmetic, fee models, identity rules, access control, player-protection limits
Mutation harnesses79Prove each safety check is capable of failing — see below
End-to-end suites3Complete player journeys against a real database
Live verification drivers79Exercise the running platform in a real browser
Operational tooling40Audited, read-only or single-purpose administrative procedures

Mutation testing

A test that passes proves only that the system behaves correctly today; it does not prove the test would notice if that stopped being true. A check that can no longer fail is indistinguishable from one that is working, and is the more dangerous of the two because it is trusted.

50pick therefore maintains 79 mutation harnesses. Each one takes a copy of the platform, deliberately introduces a specific defect into it — removes a limit, inverts a comparison, disables a lock — and then requires that the corresponding safety check detects it, by name. A defect that goes undetected is treated as a finding against the check, not against the experiment.

This is applied to the controls that matter most: that a pool always balances to zero, that a fee is never taken from a refunded stake, that a stake after the close is refused, that a withdrawal above the review threshold cannot be released by one officer, and that a limit a player has set is enforced by the server.

REAL-TIME MESSAGING

Server-Sent Events over HTTPS deliver live updates to the player's screen; Redis publish/subscribe carries them between application instances.

TABLE 11 — The real-time channel
PropertyValue
Transport to the browserServer-Sent Events over HTTPS
AuthenticationSession validated before the stream opens; refused without one
Keep-alive15-second heartbeat
Between instancesRedis publish/subscribe on a dedicated channel

What travels over it

Live market and round prices as stakes join either side; a round's result the moment it settles; a player's wallet balance when it changes; and notifications addressed to them. Messages are typed, and the channel accepts only the fixed set the platform defines.

Messages are scoped: a balance update reaches the account it belongs to and no other, while market and round updates are public and broadcast. A connected browser cannot subscribe to another player's private stream.

Why Server-Sent Events rather than WebSockets

Live data flows in one direction: server to player. Every action flowing the other way — placing a stake, cashing out, requesting a withdrawal — is a separate authenticated request that must be validated, rate-limited and audited in its own right, and would be neither safer nor faster over a persistent socket.

For one-way delivery, Server-Sent Events are the more robust choice on the networks Tanzanian players actually use. The channel is ordinary HTTPS, so it passes through proxies and mobile intermediaries that interfere with socket upgrades; the browser reconnects by itself after a signal drop; and it inherits the same transport security, authentication and rate limiting as every other request.

Delivery across instances

A player's browser is connected to one instance, but the event that concerns them may be produced by another — a settlement is performed by whichever instance holds the scheduling lease. Each instance publishes its events to a Redis channel; every instance subscribes and forwards what is relevant to the players connected to it.

A publisher also receives its own message, so an event is emitted locally once and relayed once, and a message arriving back from the channel is not republished. A settled round reaches every connected player exactly once, whichever instance settled it.

The channel is a convenience, never an authority. A live update tells a player's screen that something has changed; it never decides what changed. Balances, results and payouts are read from the database and settled by the server, so a player who loses connectivity sees the same outcome on reload as one who stayed connected throughout.

Security architecture

Session lifecycle

A session is a signed cookie, validated against the database on every request rather than trusted on its face. One session is honoured per account at a time: signing in on a second device ends the first, and the ended session is refused on its very next request rather than lingering until it expires. A password reset ends every session the account holds.

Sessions rotate on sign-in, so a session identifier observed before authentication cannot be reused after it. A cookie whose contents have been altered fails signature verification before any handler reads it, and the attempt is recorded.

Proven by attack

The security controls are not only implemented; they are attacked on a schedule and required to hold. Every administration route was exercised against a role not permitted to reach it and refused in every case. Session cookies that were forged, emptied or filled with garbage were rejected without reaching a handler. Path-traversal attempts returned nothing. And 79 mutation harnesses each remove or invert one specific safety check — a limit, a lock, a comparison — and require the corresponding control to notice, by name, so a control that has quietly stopped working cannot pass for one that works.

Defence in depth

No single control is relied upon, and defeating one does not defeat the platform. A stolen password still meets the second factor; a forged cookie fails signature verification before any handler runs; a request that survives authentication still meets a server-side permission check for that specific action; and a privileged action that succeeded regardless would still be written to a chain in which each entry is cryptographically linked to the one before it, so a later edit or deletion is detectable rather than silent.

Separation of duties

The platform's most consequential actions are structured so that one person acting alone is not sufficient. A withdrawal at or above the review threshold requires two different compliance officers to approve it before any payment instruction is created, and a stricter two-officer market-resolution mode is available as a configurable option. Both are enforced by the server, not by procedure.

Data residency & retention
10

DATA RESIDENCY, PROTECTION & RETENTION

Where data is held, how it is protected, and how long each kind of record is kept.

Where data is held

The application and its database run in a United States region. Identity documents and database backups are held in a Western European region, in two separate stores under separate credentials. Both are encrypted at rest.

Identity documents

Document images are stored as encrypted objects and are never served directly. A compliance officer viewing one receives a signed link valid for a short, fixed period, and every view or download is written to the permanent record with the officer's identity and a timestamp.

TABLE 13 — Retention periods
RecordRetained
Transactions, ledger entries, position history7 years
Identity documents and decisions7 years from account closure
The permanent action log7 years, not editable or deletable early
In-app notifications180 days, then purged automatically
Marketing-consent records2 years from last activity

A player's own data

A player can export a complete copy of their own data from their profile at any time. Requests to correct or erase personal data are submitted the same way and reach a compliance officer within the statutory period.

Erasure is handled so that it does not defeat a control that exists to protect other players. Because the identity-document number is what prevents one person opening several accounts, a closed account's number is irreversibly transformed into a value that can still be compared against a future submission but can no longer be read. The document images themselves are deleted outright.

Note — §10

Retention is enforced by mechanism, not by policy alone. Records subject to the seven-year requirement are held in structures that no automated process is permitted to delete, and the permanent action log is append-only by construction rather than by convention.

Resilience & continuity
11

RESILIENCE, BACKUP & CONTINUITY

The platform is designed to lose a component without losing a transaction, and every backup is proven by restoring it.

Backups

The database is backed up nightly on an automated schedule, encrypted, and shipped to storage separate from the live system. Each backup is then restored into a disposable database and checked against the original before it is trusted. A backup that has never been restored is an assumption; one that has been restored and verified is a fact, and the platform treats the distinction as material.

The restore procedure has been rehearsed end to end against a full production-scale copy, so recovery is a practised operation rather than a first attempt made under pressure.

TABLE 14 — Continuity measures
MeasureHow it works
Multiple instancesThe application runs as more than one interchangeable instance; any one can be replaced without interrupting play.
Single execution of scheduled workTime-driven money work is claimed by one instance under a self-expiring lease, so it runs exactly once and resumes automatically if that instance stops.
Forward-only migrationsAn instance starts only after its schema migrations have applied successfully, so a release can never serve traffic against a schema it does not expect.
Nightly verified backupEncrypted, stored separately, and restore-checked before being trusted.
Payment-route healthA route that cannot be reached is closed to players in their own language rather than accepting a request the platform cannot fulfil.
Uncertain payouts held openA payout the network can neither confirm nor deny is never assumed failed; the position is held rather than risking a double payment.

Degrading safely

Where a dependency is unavailable, the platform's response is to refuse clearly rather than to proceed uncertainly. A withdrawal cannot be requested against a payment route that is down. A market cannot be published against a source that has not been approved. A settlement that cannot be completed in full is not completed at all.

The principle behind each of these is the same: in a system holding players' money, an honest refusal is always preferable to an action whose outcome is unknown.

12

OBSERVABILITY & MONITORING

Faults are surfaced by instrumentation rather than by players reporting them.

TABLE 15 — Monitoring surfaces
SurfaceWhat it reports
Error monitoringApplication errors and performance telemetry, captured by Sentry and tagged by environment. Hosted in a European region.
Internal health endpointLive state of the database, cache, email provider and payment subsystem, plus which instance holds the scheduling lease.
Audit chainA durable, tamper-evident record of every privileged action, which doubles as the forensic trail for any later investigation.

Diagnosing a failure after the fact

When a deposit fails, the payment network's own reason code and message are recorded in the audit payload rather than discarded. This matters because a failure that leaves no explanation cannot be investigated later; the record survives log rotation and can be produced for a specific player and a specific transaction on request.

What monitoring does not receive

Error telemetry carries the technical context needed to diagnose a fault. It is not a channel for player records, identity documents or financial history, all of which remain within the platform's own database and object storage under the controls described in Section 10.

Note — §12

Reconciliation is continuous, not periodic. The double-entry ledger and the wallet balances are checked against each other on a running basis rather than in an end-of-day batch, so a discrepancy is detected close to the moment it would have arisen rather than after a day of activity has been layered on top of it.
