## 1. Findings, worst first

### 🔴 S-01 — `formatTzsCompact` picks its magnitude branch BEFORE it rounds, so a figure between 999,500 and 999,999 prints as `TZS 1000K`

`src/lib/utils.ts:36-44`

```js
if (abs >= 1_000_000) return `TZS ${sign}${(abs / 1_000_000).toFixed(...)}M`;
if (abs >= 1_000)     return `TZS ${sign}${Math.round(abs / 1_000)}K`;   // 999_500 -> "1000K"
```

The guard asks "is it a million yet?" against the **raw** value, then rounds inside the
thousands branch. Measured:

| input | prints | should print |
|---|---|---|
| 999,499 | `TZS 999K` | `TZS 999K` (ok) |
| **999,500** | **`TZS 1000K`** | `TZS 1.0M` |
| **999,999** | **`TZS 1000K`** | `TZS 1.0M` |
| **999,500,000** | **`TZS 1000M`** | `TZS 1.0B` |
| **999,999,999** | **`TZS 1000M`** | `TZS 1.0B` |

Same defect at the B seam, because `.toFixed(0)` on `999.5` is `"1000"`.

**Why it matters and is not theoretical.** This is the file's own "THE ONE COMPACTION
GRAMMAR FOR MONEY ON THIS PLATFORM", and it has **37 call sites across 13 files**. Two of
them are the most-seen numbers we publish:

- `src/components/home/landing-hero.tsx:141` — the sum of open pools, the landing proof rail
- `src/app/markets/page.tsx:168` — open volume on the board

The sum of open pools crossing one million is an ordinary Tuesday. There is a
500-shilling-wide band where the hero says `TZS 1000K` — a grammar this platform does not
have, in the one place we ask a stranger to trust our numbers.

**Fix:** round first, then branch (or promote at 999,500 / 999,500,000). One expression.

**Prove it RED first:** assert `formatTzsCompact(999_500) === "TZS 1.0M"` and
`formatTzsCompact(999_500_000) === "TZS 1.0B"` in a new `test:money-format` — both fail
today. Do NOT assert the *shape* (`/^TZS \d+(\.\d)?[KMB]$/`) — `TZS 1000K` matches it.

### 🔴 S-06 — `/admin/candidates` has a primary Search button that does nothing, and after a Clear it DELETES the officer's query

`src/app/admin/candidates/candidate-filters.tsx:44, 73-79`

```jsx
const [search, setSearch] = useState(currentSearch);   // never written again except by Clear
// ...
<SearchBox ... />                                      {/* owns its OWN state, mode="url" */}
<button onClick={() => push({ q: search })} className="btn btn-primary ...">Search</button>
```

`SearchBox` in its default `mode="url"` holds its input in its own `q` state and pushes to
the URL on a 250 ms debounce (`src/components/ui/search-box.tsx:79, 98-102`). It takes no

Two consequences, both live:

1. **The button is inert.** Clicking Search re-pushes the query already in the URL.
2. **After a Clear it is destructive.** `setSearch("")` pins `search` to `""` for the rest
   of that mount. The officer then types `Simba` (the debounce writes `?q=Simba`), clicks
   the big primary **Search** button — and `push({ q: "" })` **wipes it**. The strongest
   affordance on the rail undoes the work.

This is copy-paste residue. `poll-filters.tsx` is the same file with the button removed when
it adopted the debounced `SearchBox` — its comment at `:65-67` records exactly that. The
candidates clone kept the button and inherited none of the wiring.

**Fix:** delete the button. Then delete the now-dead `search`/`setSearch` state from
**both** files — it is dead in `poll-filters.tsx` too (`:45`, only ever `setSearch("")`).

**Prove it RED:** a live drive that types a query, clicks Search, and asserts `?q` survives.

### 🟠 S-18 — a destructive write that swallows its own failure, then audits that it succeeded

`src/lib/server/updown-dal.ts:637`

```js
async delete(id) { await pc().upDownChain.delete({ where: { id } }).catch(() => {}); },
```

The `.catch(() => {})` discards every error and returns `void`. `deleteChain`
(`updown-config.ts:1229`) never reads back, so a delete that hit a FK violation, a dropped
connection or a missing row still returns `{ ok: true }` **and writes the
`updown.chain.deleted` audit row.** The audit log would assert a deletion that never
happened — on a control whose entire purpose is to be answerable to the Gaming Board.

⚠️ Same shape the reset script's own comment already records: *"the deletion landed and the
audit row did not… and the script still printed ✅, because it verified the DELETION and
never the audit."* Here it is the mirror image, which is worse: the audit says yes and the
data says no.

**Fix:** let the error propagate, and have `deleteChain` **read back** (`count === 0`)
before it writes the completion row. Any destructive write must verify its own effect
before claiming it.
**Prove it RED:** make the delete throw and assert no `updown.chain.deleted` row is written.
