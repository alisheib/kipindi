## Premises found false (13)

- 'network' pill is FALSE by the platform's own ruling: the operator is the RANGE HOLDER, not the network, because number portability has been live since March 2017 (src/lib/tz-msisdn.ts:18-20). U20 already labels the column 'Operator (by prefix)' (src/app/admin/contacts/page.tsx:162). U38 must say 'Operator (by prefix)', never 'network'.
- 'The split, server-counted' assumes something that can count cheaply. Nothing can. The gate is per number, with 3 single-key reads before any decision: suppression.find (consent.ts:181), user.findByPhone (:187) and messagingConsent.latestFor (:138/:239). For a consenting player it adds RG reads plus harm markers, which read up to 10,000 transactions (src/lib/server/responsible-gambling.ts:824). Neither twin has a bulk read: the store has only single-key `latestFor` and `find` (src/lib/server/store.ts:2454-2457, 2512-2528; prisma-dal.ts:3392-3397, 3457-3464). At 150k numbers that is about 450k round trips before the residual. U38 must add batched reads and a budget, and report what it did not check.
- 'matching' assumes a resolver that covers players. None does. U24's `contactAudience` is the CONTACT book only (plan :2089-2094), while OD6 says the audience UNIONS the book and the player table on the one key (plan :882-883). U42 names two walks (plan :2273). No unit owns the player arm or the de-duplication. U38 is the first unit that needs them.
- 'every reason line named and counted' conflicts with U20's shipped ruling. Responsible-gambling, age and account refusals read 'Not reachable' and are never itemised for GROWTH (src/app/admin/contacts/page.tsx:63-79 REACH map; header :14-15). Combined with the ≤5 enumerate of U40, an itemised count would identify a person's protected standing. U38 names one 'protected' line covering six reasons (rg_self_excluded, rg_cooling_off, rg_harm_marker, rg_under25_history, age_minor, account_status) and itemises only the reasons an operator can act on.
- 'describeAudience … the page a month later' cannot work on a filter built from URL presets. `range=7d` is relative (date-range.ts:216), a custom window is silently capped to 400 days (date-range.ts:36, :159), and a list can be renamed, or its members cascade-deleted (schema.prisma ContactListMember onDelete Cascade). The stored filter must carry ABSOLUTE instants plus the label in force, and the list NAME as a snapshot. describeAudience must stay pure over that shape.
- A trap that is not stated: both the DateTimeRangeFilter (datetime-range-filter.tsx:62 `defaultPreset = "7d"`) and resolveRange (date-range.ts:140 default `"7d"`) default to LAST 7 DAYS. A bare audience URL would quietly mean 'joined in the last 7 days' unless both are given `all`.
- 'A sample of five … in the enqueue's own order': there is no enqueue (U42, S22). The order exists only as plan prose. The only way to make the claim true is for U38 to OWN the ordered walk (`walkCampaignAudience`, with a phase-prefixed cursor exactly as U42's text asks, plan :2273-2275) and for U42 to consume it.
- The callout's reasons are incomplete. Since U11, every book-only contact is refused `age_unknown` until U33 records an 18+ attestation (consent.ts:246-251), whatever its consent. Old-wording yeses are also `no_consent` (consent.ts:141). A callout that blames only 'no permission on record' is false for the contact book on day one.
- OD26 says counts are always a `groupBy` over rows. The will-receive split cannot be a SQL groupBy, because the gate's order and RG logic are application code. It is an in-process reduction over gate verdicts, still with no stored counter. Only `matching` and the KPIs are row counts.
- Vocabulary collision: U20's 'Reachable' column means the GATE passed (page.tsx:81-89 `reachOf` → 'Reachable'), which is U38's 'will receive'. Two surfaces would use one word for two facts.
- Membership oracle already present: U20 shows a per-row 'Player' chip to every role (src/app/admin/contacts/page.tsx:183). D19 (plan :1260-1261, U30 :2142-2143) rules that masked roles get COUNTS, never a per-row player flag. U38's sample must not repeat it for book rows. The U20 chip is recorded as a risk, not fixed here.
- `test:read-tiers` and `test:client-graph-safe` are NOT in `predeploy` (package.json:30, :33; absent from the chain at :300). A masking or boundary claim that leans on them gates nothing at deploy. `test:campaign-audience` must carry its own source assertions for both.
- The 'next free dal-parity section is §21' is true TODAY (highest is §20 at scripts/dal-parity.test.mts:1539). But U29 (S14) and U35 (S17) each take 'the next free number' before U38 (S18), so U38 should expect §23 and re-derive it at build time.
