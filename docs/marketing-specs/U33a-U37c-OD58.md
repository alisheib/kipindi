## 0 · The decisions in one screen

1. **A recorded basis is never a ledger row.** The consent ledger stays the person's own word (GIVEN or WITHDRAWN). The
   licence basis has its own records. For non-members it is an append-only basis per list (`ContactListBasis`). For
   players it is one owner-controlled record (`marketing.outreach.licence`). dal-parity §20.0's population of ledger
   writers does not grow. That is the structural proof that nothing writes a consent the person did not give.
2. **One master record, CLOSED by default.** Every non-consent basis counts only while `marketing.outreach.licence` is
   OPEN: a never-asked player, a listed contact, a typed test. Opening it is an audited admin act. It is refused until
   the Privacy Notice and the RG page no longer contradict it and the pre-ledger switch-offs are reconciled. Closing it
   is one click and takes effect at once.
3. **With the record CLOSED, the gate answers as it does today**, byte for byte, for every player. For contacts it gains
   only what U33 always planned: a consented contact with 18+ evidence becomes marketable. So every unit ships with zero
   production change.
4. **Players need no list.** The account is the player's record: the age comes from the date of birth and the identity
   check, and the number came with the account. Lists are for non-members, and each list carries an officer's 18+
   confirmation.
5. **KEPT regardless of the record:**
   - any active stop, asked first as today;
   - a WITHDRAWN latest ledger row;
   - a switch turned off after a consent;
   - RG standing (rg.ts is untouched, and a licence basis never counts as "opted in again");
   - under 18, and an unknown age;
   - the "50pick" opening and the stop link (the renderer);
   - U13 and U14 once they are built.
6. **U37c** takes `(campaignId, variant, recipient)`. The recipient is the officer's own number (the one-tap default) or
   a typed `{ number, adultAttested }`. The test uses the same gate, the same `dispatchSlice` and the same `sendBatch`
   (D15). For a typed number:
   - it always renders as a contact-book recipient: the `{jina}` fallback and the source line;
   - its stop link never reaches the officer;
   - a masked role gets one neutral sentence;
   - the typed option opens only with the record.
7. **The owner rule.** These become persisted, validated, audited config edited on /admin/system: the basis wordings,
   the 18+ confirmations, the third-party notice, the source line, the RG §4 line, the Privacy Notice's marketing lines
   and the profile's outreach note. Code keeps the keys, the rules and the defaults. A default is a suggestion and is
   never evidence.

## 2 · Decisions (record as OD59 onward when built)

**S1 · The licence basis is its own record, never a ledger row.** A ledger row is "what one person was shown and what
they answered" (schema.prisma:3177–3184). A non-consent row there would become the person's LATEST row and speak over a
real GIVEN or WITHDRAWN. That is exactly why a ledger UNKNOWN was rejected (OD9, corrected). A new status value would
also be a 55P04 two-step. *Rules out:* any `MessagingConsent` write for a licence basis or a test attestation, and any
`marketingOptIn = true` write for outreach.

**S2 · One master record, `marketing.outreach.licence`, CLOSED by default.** It is a `defineConfig` record with an admin
card. Every non-consent basis is honoured only while it is OPEN. Opening is validated (§5.3) and audited. Closing is
immediate and audited. *Rules out:* a code-constant switch, and a per-campaign flag that a send loop could forget.

**S3 · A player is reached under the licence without a list. The account is the record.** The age is the date of birth
plus the identity check (code unchanged). The number came with the account, so no source line is needed (OD49). Lists
exist for non-members. (Q1.)

**S4 · A player's own stop is honoured whatever the record says.** It is either of these:
- the latest ledger row is WITHDRAWN, whatever its source: the person's switch, /s/, an officer recording the person's
  call, an erasure, or U16's future lapse row;
- `marketingOptIn` is false while the latest row is GIVEN. That is a switch turned off with no withdrawal row; today
  only the two-year lapse produces it.

An active suppression of any reason is asked first, as today. U33a-0 reconciles the E-409 switch-offs (F1) before the
record can open. *A deliberate narrowing:* a WITHDRAWN written by a previous holder's erasure blocks licence outreach to
the new player at a recycled number. That player's own tick still works.

**S5 · Closed-record parity.** While the record is closed, every player's verdict is byte-identical to today, reason
and detail alike. Contacts change only as U33 planned:
- (a) a consented contact with 18+ evidence is ALLOWED, with basis CONSENT;
- (b) a contact whose latest GIVEN names no SMS and is not an import attestation gets `no_consent` (today it gets
  `age_unknown`);
- (c) a consented contact with no 18+ evidence keeps the reason `age_unknown`, with a re-worded detail.

Nothing in production writes 18+ evidence before U33b-L, so (a) is dormant.

The gate also READS exactly as it does today while the record is closed:
- a player whose toggle is off is refused before any ledger read (the `seen` out-parameter, §3.4);
- a contact with no consent is refused before the new standing read.

So the split's figures past its time budget do not move either. The one exception is a consented contact (rare while
closed): it now needs the standing read for its 18+ evidence, so past the budget it reads `unchecked` where it read
`age_unknown`. That is the honest direction.

**S6 · A new skip reason, `no_basis`.** It covers two cases: a non-member with no consent and no covering basis while
the record is OPEN, and an erased tombstone under any licence basis. The split maps it into the existing `no_consent`
bucket, labelled "No consent or recorded basis" in U38b. There is no sixth bucket, so no new aggregate oracle (OD53's
spirit). The readers' column on the contacts page says "No recorded basis".

**S7 · Every ALLOWED verdict names its basis:** `{ ok: true; basis; basisRef }`.
- The basis is `"CONSENT" | "LICENCE_PLAYER" | "LICENCE_LIST" | "LICENCE_TEST"`.
- `basisRef` is `ledger:<row id>`, `outreach:<recordedAt>`, `list-basis:<id>` or `test:<attemptRef>`. It holds ids
  only, never a number.
- `dispatchSlice` carries it on every outcome after clearance, for U43's gateTrail (M6).
- The test's audit row records the basis. It also records the ref for the three kinds whose ids hold no digit run
  (`outreach`, `list-basis`, `test`), but never `ledger:<id>`. A ledger id is 32 lowercase hex characters
  (ledger-stamp.ts:50), so it often holds a run of nine digits that a phone-run detector or a future scrub would read as
  a number. The gateTrail keeps the full ref.
- ⛔ The basis NEVER reaches the browser. LICENCE_PLAYER against LICENCE_TEST would tell a masked officer whether a typed
  number is a player's (A32).

**S8 · List coverage.** A basis covers a number when all of these hold:
- the number's LIVE book row (never the erasure tombstone) is a member of the basis's list;
- the member was added at or before `recordedAt` (`addedAt <= recordedAt`, compared as instants);
- the basis is not revoked.

The newest covering basis is the ref (recordedAt desc, then id desc). Recording again covers everyone on the list at
that instant. Members added later are not covered until the next recording. Leaving the list, or the book, ends the
coverage. *Rules out:* a basis that quietly covers numbers nobody confirmed.

**S9 · No licence basis reaches an erased tombstone.** A list basis or a test attestation gets `no_basis` there. Only a
new real consent reaches that number, and a new player at that number is governed by their own account. *Why:* U18b
writes no stop, on purpose, so that a recycled number's next owner can consent. So the tombstone itself must refuse
outreach.

**S10 · A non-member's 18+ evidence** is one of these, and is never inferred:
- the 18+ confirmation of a covering list basis;
- the latest row itself being a first-party import attestation (`isImportAttestation`);
- the attestation of the one test in progress.

A player is always governed by their date of birth and identity check: the attestation never reaches the player branch.
The walk past a person's own stop (U33.md's `attestedSinceErasure`) ships with the import track (U32), when the first
import attestation can exist. Until then a listed contact's stop followed by a resume stays ALLOWED, because the list
still covers them.

**S11 · rg.ts is untouched.** Its "consented again after the break or the restore" reads the ledger only, so a licence
basis never satisfies it. A never-asked player whose break has ended stays refused (`rg_cooling_off`) until they tick yes
themselves. That keeps the RG page's "until they opt in again after it ends".

**S12 · The gate gains a fourth parameter, `context`.** Its default is a frozen empty object. Its only member is
`testAttestation`:
- it is honoured only in the contact branch;
- it counts as the basis LICENCE_TEST only while the record is open;
- it is also 18+ evidence for that one call;
- only `campaign-test-send.ts` may construct it (a structural guard).

The send loop goes on calling the gate with one argument.

**S13 · The gate's reads grow by two:** `outreach()`, which is the record, and `bookStanding(msisdn)`, which returns
`{ row: "none" | "live" | "erased"; cover }`. The split answers both in bulk: the record once per chunk, and
`standingAmong` for the chunk's numbers that no account holds.

Past the time budget, `bookStanding` throws like the other database reads (`unchecked`). `outreach` keeps answering
the value the split already read. It is a cache read, not a database read, and refusing it would turn every
toggle-off player past the budget from `no_consent` into `unchecked`, which would break the closed-record parity
(S5).

**S14 · The wordings move into `marketing.wordings`.** It holds versions with an append-only history, edited on an admin
card. A basis is recorded only from a SAVED version: a code default is a suggestion, never evidence. An import
attestation is recognised against any saved pair of versions. This replaces `CONSENT_BASIS_G4` and OD50's static import
ban with a refusal at runtime. The intent is kept: nothing unconfirmed reaches evidence. "Confirmed" now means "saved by
an admin, and audited".

**S15 · The public lines move into `legal.policy_lines`,** edited on an admin card:
- the RG §4 marketing bullet;
- the Privacy §3 consent bullet;
- a new Privacy §3 licence bullet;
- the Privacy §4 SMS-gateway bullet;
- the profile's outreach note.

The defaults are today's text, so nothing changes until a save. A save is checked against `KEPT_PROMISES` (a code map
that test:rg-policy holds true) and against the processor words test:privacy-notice requires. Saving moves the page's
version.

**S16 · The source line (G5) gets an editable home:** the key `source.phrase` in `marketing.wordings`, checked by the
renderer's own source-line rules. Every save of a DRAFT stamps it into that draft. The words themselves stay Ali's
(G5), but entering them no longer needs a code change.

**S17 · U37c's input** is `(campaignId, variant, recipient)`, where the recipient is `{ kind: "own" }` or
`{ kind: "typed"; number: string; adultAttested: boolean }`. A missing recipient means own, so a page left open from the
previous deploy keeps working.

**S18 · A typed number always renders as a contact-book recipient:** the `{jina}` fallback, never the holder's first
name, plus the source line. The text is the same for a player as for a non-member. It is refused up front, whatever the
number, while the campaign has no source line.

**S19 · Typed tests need the record OPEN.** While it is closed they are refused whatever the number. *Why:* with the
record closed, only a consenting number could pass, so "handed over" would tell a masked officer that the number has
consent, which mostly means a player.

**S20 · The officer confirms 18+ for EVERY typed number.** They are never told whether the number is a player's. The
confirmation is a saved wording version, recorded in the audit row. It is never written to the ledger or to the book.

**S21 · A typed test asks the gate before anything is minted.** This pre-check is the same function with the same
context, and `dispatchSlice` asks the gate again before the send. A refused typed number leaves no token row and no
`SmsMessage` row. An RG refusal at the pre-check writes the same COMPLIANCE row that `dispatchSlice` writes, through one
exported helper.

**S22 · The recipient's stop link never reaches the officer.** The returned text is the dry render with the measurement
token (`/s/xxxxxxxx`). Only the wire gets the real token.

**S23 · D19.** For every gate refusal of a typed number, a masked viewer gets ONE sentence and ONE reason value,
`typed_refused`. A reader gets the reason, with the protected reasons collapsed into one line (U38a's rule). The consent
link shows only for the officer's own number.

**S24 · Two more budgets for typed tests.**
- **Per recipient, `marketing.testSendTo`:** 5 at once, then one every two hours, keyed by a hash of the gate's key.
- **Per officer, for typed tests only, `marketing.testSendTyped`:** 10 at once, refilling 10 a day.

Both sit beside the officer's own `marketing.testSend` (3, then one per 10 minutes). Without the second, an officer could
run a quiet one-to-one campaign of about 150 messages a day to strangers through "tests", outside U40's confirmation and
U14's cap (A33). Both are spent only after the number-independent checks (§3.7), so a closed record or a missing source
line never drains them.

**S25 · A response floor.** Every typed outcome decided at the gate or after it returns no sooner than
`TYPED_TEST_MIN_MS` = 3000 ms after the request began. That stops the player branch's longer reads (the identity check,
the harm scan) from timing out as a player signal.

**S26 · Tests stay outside U14's cap** (M12 kept). S24 bounds typed tests instead. Both obey U13 once it exists.

**S27 · The profile switch reads ON for a player the licence reaches** (`outreach: true`) and OFF for any active stop.
Turning it OFF records their stop (a WITHDRAWN row), exactly as today. The explanatory note is a policy line, shown once
an admin saves one.

**S28 · DSAR.** A player's export says when they are messaged under the licence (the basis, and since when). It never
invents a consent row.

**S29 · U23's Suppress already records a GBT instruction as an OPERATOR stop.** An optional U23c adds a fixed "why"
token (Officer's decision · Gaming Board instruction). The gate does not change.

**S30 · Agent referees (P20).** Either the owed control U33r is built before the import track, or Ali re-words the
privacy line (Q8).

**S31 · The doc amendments ship with each unit:** §5.1, OD7, OD9, OD14, OD55, M12, U38's callout, and G4 and G10
(Appendix C).

## 4 · (b) Schema changes, the migration, and the deploy order

### 4.1 Why the ledger cannot be reused

The task asks first whether the ledger can carry a basis kind. It cannot do so without becoming a consent:
`MessagingConsentStatus` is `GIVEN | WITHDRAWN` (schema.prisma:3137–3140), and the gate reads the LATEST row. A third
status would have to be added in its own migration one deploy ahead (55P04). Worse, it would become the person's latest
row and speak over their real word. It would also be per number, while the ruling records the basis per list. So: one
new table. The master record and the editable texts are SystemConfig rows written through `defineConfig`, which needs no
migration.

## 5 · The editable values (the owner rule, 2026-10-03)

Each record follows the precedent that ships: `defineConfig`, a verified setter, validation that runs on the server
before any write, an audit row of `{ before, after, changes }`, a hint, and a card on /admin/system behind
`requireAdmin`. A refusal names the field (`fieldError`). Every problem is listed at once and the form is kept. There is
no lock and no disabled box.

⛔ **Each record passes its own `merge`.** The factory's default is a shallow spread, and that would be wrong for all
three:
- **The outreach record REPLACES the whole object** on every set. A spread would carry `closedBy` into a re-opened row,
  and the strict reader (§5.3) would then read the re-opened record as CLOSED.
- **The wordings and the lines replace only the keys the server rebuilt.** The server builds the full version array of
  a changed wording, or the full en/sw/zh object of a changed line. It never spreads a nested object.

test:licence-outreach R4b proves the first: open, close, then open again reads OPEN.

### 5.1 `marketing.wordings` — the "Marketing wordings" card

- **Shape:** `{ versions: Record<WordingKey, WordingVersion[]> }`, where
  `WordingVersion = { v: number; text: string; savedAt: string; savedBy: string }` and the newest is last.
- **Never saved:** `[]`. The card then shows the code default, prefilled as a suggestion, and no writer can record it.
- **The audit action:** `config.marketing_wordings_updated`.
- **Saving:** a version is appended only when the text changed. The SERVER builds the version, never the browser. A
  POST that tries to change or drop a past version is refused, nothing is written, and no audit row is made.
- **Hints:**
  - "From your save, new records use these words; records already made keep the words they were made with."
  - For a basis: "This sentence is shown to the person if they ask for their data."

**Every key is checked for these first:**
- the text is normalised: NFC, invisible format characters removed, each run of whitespace made one space, trimmed;
- no `<`, `>`, `{` or `}`;
- refused if the ONE phone-run rule (`holdsPhoneRun`) finds a number in it.

**Then each key's own rules:**
