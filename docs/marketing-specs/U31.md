## Premises found false (10)

- 'decide() reads ERASURE_EVIDENCE' does not work as things stand. The constant lives in src/lib/server/marketing/erase.ts, a server module (erase.ts:1 imports `db` from store). The Accept line needs the SAME decide() behind the browser's Apply label, and U27's boundary guard forbids a client contacts file from reaching src/lib/server/**. FIX: move the declaration to a pure src/lib/marketing/erasure-mark.ts; erase.ts imports it and re-exports it.
- '⛔ Consent is never written by an import path' contradicts U33 (plan:2175 'First-party bases write GIVEN ledger rows') and OD9 (plan:954). The rule that is both buildable and consistent: decide() itself never writes consent. An EXISTING book row never gets a consent write from an import. For a CREATED row only, U33 may append a basis row, and only where decide() returns consentWritable=true: the latest ledger row is not WITHDRAWN, the number is not on the stop list, and no player holds the number. The §9 wording must be rewritten in the same commit.
- Nothing structural stops an importer writing consent today. MarketingContactPatch (store.ts:510-515) allows consentState, suppressedAt, userId, source, sourceRef, importId and rawInput. U31 must narrow the import's write to a NAMED patch type limited to displayName/email/notes/tags (+ updatedBy).
- 'A row whose contact is suppressed' cannot be read from the book. `suppressedAt` is documented as a cache (schema.prisma:3346-3348), and NO production code writes it: grep finds only the dev seed (route.ts:78). stopMarketing and erase.ts never mirror into the book. So a contact who used /s/ to stop has suppressedAt = null. decide() must be fed `db.suppression.find(key) !== null`, never the cache.
- The erasure mark is NOT durable on its own. It lives only on the emptied book row. erase.ts:109 writes the ledger's WITHDRAWN(evidence 'erasure') only when the latest row was GIVEN, so the ledger carries the mark only some of the time. U23's 'remove' (plan:2077) can delete an emptied row, after which re-importing an old spreadsheet would CREATE the erased person's name again. Needs a U23 rule (refuse to remove a sourceRef='erasure' row) and a decide() create-path check on the ledger's erasure row (partial cover).
- Guard key `test:contacts-import` does not exist in package.json (grep empty). U25 is planned to create it at S12. Today there is no src/lib/contacts/, no src/lib/server/contacts/ and no ContactImport model (grep schema/store empty). File row numbers, ParsedContactsFile, CONTACT_FIELDS and the staged run row are all ASSUMED from U25/U28/U29/U30's §9 text.
- Every import write is a read-then-write race. The DAL update is unconditional (prisma-dal.ts:3583-3610; store.ts:2607-2613). Sequence: the importer reads a row, an erasure empties it, then the importer writes the old name back. OD32's own principle is 'the index, not a pre-check that can be raced', so the import's update must be CONDITIONAL. Today no such DAL method exists.
- OD11's note (plan:965-966) still says the re-arm precedence and the lift reason filter are 'owed before U16/U23'. Both are shipped (store.ts:2486-2501, 2545; prisma-dal.ts:3434, 3472-3478). The note is stale and should be corrected in U31's docs pass.
