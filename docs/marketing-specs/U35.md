## Premises verified true (13)

- D22 is real. `enum SmsPurpose { OTP INVITE OPS }` has no MARKETING (prisma/schema.prisma:3028-3032), and neither does the memory mirror `export type SmsPurpose = "OTP" | "INVITE" | "OPS"` (src/lib/server/store.ts:329).
- Adding MARKETING needs no change to sms.ts and breaks no exhaustive switch. `sendBatch` defaults a missing purpose to OPS (src/lib/server/sms.ts:734). The cost-floor exemption fires only when every message is OTP (sms.ts:694), so a MARKETING batch is floor-subject automatically. A grep for `Record<SmsPurpose` or any enumeration of the values finds none in src/ or scripts/.
- The tables do not exist yet. The only reference to the name is in U9: `DISPATCH_TARGET_TYPE = "SmsCampaignRecipient"` (src/lib/server/marketing/dispatch.ts:61), and `send` has no default until U35 provides an honest purpose (dispatch.ts:36-41). dispatchSlice settles by `ref`, which is passed to sendBatch as `targetId`, so the recipient `id` IS the ref.
- The 55P04 rule is real. A value added to an EXISTING enum cannot be used in the transaction that adds it, so it must live in its own migration file. Precedent: prisma/migrations/20260728100000_rbac_roles/migration.sql:7-11, whose comment says so and which splits the files. The U18a migration repeats it (20260928170000_marketing_contact_book/migration.sql:25-27). A brand-new TYPE may be created and used in one file.
- MarketingContact exists with a cuid `id` (schema.prisma:3319), so it is a valid `contactId` FK target. Its own `userId` uses `onDelete: SetNull`, never Cascade, which sets the house style for the recipient's two links.
- §10 of dal-parity is taken, as the plan says (scripts/dal-parity.test.mts:608, 'the market reopen stamp'). §20 is the last section (:1539) on both the worktree and origin/main, so §21 is the next free number today.
- Counts come from groupBy and are never stored (OD26). U20's whole-book `summary()` is the shipped precedent.
- `red:dal-parity` mutates a COPY of the tree through KP_SRC and never writes the repo (scripts/red-dal-parity.mjs:7-11), so it is safe on this laptop. Its FILES list (:32-41) must name every file the gate reads.
- `test:migration-ownership` inspects DROPs only, so a purely additive migration passes it trivially (migration-ownership.test.mts:14-23). The U18a migration header (marketing_contact_book:9-12) says the same: green there is not evidence.
- `createMany({ skipDuplicates: true })` emits `ON CONFLICT DO NOTHING` with NO target (schema.prisma:3251-3253, the MarketingOptOutToken warning). It therefore swallows ANY unique violation, not just the one intended. For recipients this is safe only if a seed carries no `smsReference` and ids are cuids, so the seed type must make that structural.
- The DAL never hard-deletes a User (a grep for `pc().user.delete` finds nothing), so a SetNull FK on `userId` is belt-and-braces, not load-bearing.
- `isGatewayMsisdn` (/^255[67]\d{8}$/, src/lib/phone-normalize.ts:140) is the one-key predicate. It lets the DAL refuse a `+255…` spelling, which would otherwise defeat the unique index.
- Prisma DAL signatures must use NAMED types. `region()` takes the first `{` after a signature, so an inline object literal hands the gate a type annotation instead of the body (store.ts SmsDlrResult note, ~:368-376).

## Premises found false (8)

- §9's RED, 'drop the unique index → the U43 concurrency control must fail', cannot run at U35. There is no U43 control: no scripts/marketing-engine.test.mts and no `test:marketing-engine` key in package.json. It is replaced here by in-process plants (the migration text without the unique index, and a memory twin without the dedupe). The five-concurrent-driver control stays owed at U43, and U43 must plant the same removal.
- Even with U43's control, a 'drop the unique index' plant can never reach the schema or migration through `red:dal-parity`. dal-parity reads schema.prisma from ROOT, not KP_SRC (dal-parity.test.mts:53; §19's own note at :1439-1447). So the index needs its own in-process suite, which is why `test:campaign-models` is new.
- 'The repo already paid for this once' is only partly true. The 55P04 cost was MEASURED on embedded PG at S3b, not hit in production. The real constraint is the FILE (transaction), not the commit: 5da76fb8 shipped `rbac_roles` (ADD VALUE) and `rbac_grants` (which uses it) in ONE commit and deployed cleanly. U35 writes no MARKETING row at all, so both files could share a commit. Two commits are still recommended for an independent live proof.
- 'The next free number' is §21 only today. U29 (staging, a new db namespace, S14) comes before U35 (S17) in §10 and will probably take §21. Re-derive the number at build; it is likely §22.
- The field list's singular 'coding, segments' cannot describe OD42's campaign. That campaign has a required Swahili body and an optional English one, and each gets its own GSM-7/UCS-2 verdict from `encodingFor`/`sizeSms` (src/lib/sms-compose.ts:109,187). The columns must be per variant: codingSw/segmentsSw, codingEn?/segmentsEn?.
- The recipient field list omits five fields that shipped code and rulings need. (1) `skipDetail`: dispatchSlice's `skipped` outcome carries `detail` (dispatch.ts:49). (2) `optOutToken`: U42 ① mints one per identifier and 'a recipient with no token must not be sent to', which a WHERE can check only if the row holds it. (3) `claimedAt`: the reaper of stranded claims needs the claim's age. (4) `locale`: which OD42 variant was sent. (5) `bodyLen`: §5.8's record.
- U47's text counts 'HELD' as a recipient bucket, but the code returns held rows to PENDING. dispatch.ts:22-23 calls `held` a slice outcome that 'U43 returns to PENDING', and U43's text agrees (one campaign stop reason, never N rows). Code wins: U35 stores no HELD recipient status, and U47's bucket arithmetic must read PENDING plus CLAIMED as outstanding.
- The plan treats an audience filter as never holding ids, but OD36 says 'a ticked-row selection is expressed AS a filter'. A selection filter is an id list in disguise. U35 can store only what it is given, so refusing id-selection filters for campaigns falls to U38/U40 (or U24 exposes an `isIdSelection` predicate).
