## Premises found false (7)

- 'Batches of ≤2,000 (≈200 KB — a 5× margin under the 1 MB action limit)' holds only at about 100 bytes per row. A typical Swahili or English row (name, number, e-mail, two tags) is 120-180 bytes of JSON, so 2,000 rows is about 240-360 KB. At U28's field caps, with multibyte names and long notes, the worst case is about 6 KB per row, so 2,000 rows is about 12 MB, twelve times the ceiling. A row count alone cannot keep a batch under 1 MB. FIX: two caps, both re-checked on the server: ≤2,000 rows AND ≤200 KiB of UTF-8 JSON (5.12× under 1,048,576). The client packs greedily, keeping row order.
- 'The run row carries the buckets, the written counters' contradicts OD26 ('No stored counters', plan:1011) and the repo's own ruling against denormalised counters (prisma-dal.ts:1408-1416). FIX: every total (staged, invalid, pending, created, updated, skipped, failed) is a groupBy over ContactImportRow, in both twins. The run row carries only two compare-and-set cursors and the two figures the server cannot recount because the browser parsed the file (OD29): totalRows as declared, and unreadable.
- The pre-flight 'buckets' cannot live on the run row in any case. inBook and isPlayer depend on the book and the User table at read time, and OD31 says the pre-flight writes nothing. They are U30's read over the staged rows. The only per-row fact staging stores is the server-derived parse verdict.
- The plan describes ONE cursor, 'a cursor that is an ordinal into the rows this run owns'. Staging needs its own resume point: a tab closed at batch 30 of 75 must resume STAGING at the next ordinal (§3c.3, 'resumes at 120,000'). FIX: two ordinal cursors, `stagedThrough` and `committedThrough`. The plan's word 'cursor' is not used as a column name, to avoid any clash with Prisma's `cursor` pagination argument.
- §3c item 1 (plan:839) is stale. It says 'U23/U27 upload in chunks to a staged row, or direct to storage'. U23 is the bulk bar, and OD29 already decided the design: CSV, vCard and paste are parsed in the browser and posted as ROWS to U29's staging; XLSX goes through U27's one 700 KB action and comes back as a ParsedContactsFile. There is no storage upload path.
- The plan implies U29 ships the staging HTTP door. It cannot: test:orphan-actions (scripts/orphan-actions.test.mts:105-110, plus the KNOWN_ORPHANS ratchet at :52, where adding an entry fails) refuses any exported `*Action` in an admin action file that nothing in src/ calls. The 'use server' wrappers must land with their first caller, U30's dialog. U29 ships a server-only service that the suite drives.
- 'Guard: test:dal-parity' alone cannot prove the Accept. dal-parity is source-level, and 'a closed tab, a reload and a redeploy all leave the run resumable, and the totals come back from the server' is behaviour. A behavioural suite (test:contacts-staging, memory twin, in predeploy) is needed, plus a one-off database evidence run for the redeploy half. A memory twin cannot survive a process restart.
