- audience.ts · export function parseContactAudienceParams(sp: Record<string, string | string[] | undefined>, now = Date.now()): AudienceParse. Reads the URL keys q · consent (GIVEN|UNKNOWN|WITHDRAWN) · suppressed (yes|no) · op (licensee id, case-insensitive, canonical upper case: VODACOM|AIRTEL|HONORA|VIETTEL|TTCL|TELXER) · list · tag · source (IMPORT|REGISTRATION|OPERATOR|AGENT) · player (yes|no) · import · range (a FULL_PRESETS id, resolved to ABSOLUTE instants through resolveRange) or from/to (EAT local, parsed with parseEatLocal; a date-only `to` is inclusive of that EAT day; unreadable or inverted REFUSES; no 400-day cap). ## risks
- 🔴 Prisma `not` drops NULLs. `{ sourceRef: { not: 'erasure' } }` compiles to `"sourceRef" <> $1`, which EXCLUDES every row whose sourceRef is NULL (nearly the whole book), while the memory twin's `!==` keeps them. The twins would diverge silently, and every suite runs on memory. Use `OR: [{ sourceRef: null }, { sourceRef: { not: … } }]`, pinned by §21.null. Nothing on this laptop executes the Prisma twin, so recommend one run of §3's one-count fixture against embedded PostgreSQL 18.3 (as U18a did), through the heavy-node lock.
- 🔴 This divergence exists platform-wide in src/lib/search today: a NEGATED name term (`-asha`) keeps nameless contacts on memory (predicate.ts:71-74: an empty haystack gives !found, which is true) but drops them on Postgres (prisma-where.ts:59: `NOT: { displayName: { contains } }` on NULL gives NULL, so the row is excluded). The production list and campaign agree with each other through the one resolver, but the suite's count is not production's for negated queries. Fix in prisma-where.ts (negated arm OR column null) as a separate platform-consistency item, not inside U24.

Changing ContactPageQuery and removing summary() breaks scripts/contacts-page.test.mts (naiveLoad :185, :189) and any fixture calling db.marketingContact.* at RUNTIME only.
