## Premises found false (10)

- FALSE: 'the per-row fallback is concurrency-bounded at 6–8, because the bet admission gate is sized from the same pool'. Same-pool reasoning gives SERIAL (1), not 6–8. The pool is 40 (prisma.ts:29). Admission's default maxInFlight is pool−4 = 36 and its ceiling pool−2 = 38 (admission.ts:68-80). Invariant 1 (admission.ts:27-30) leaves only the remaining 2–4 connections for ALL non-bet traffic, and pool_timeout=10 (prisma.ts:60-77) turns starvation into P2024. Eight concurrent import writes under full bet load would make bets fail, which is the owner's red line (admission.ts:1-5). The spec uses IMPORT_DB_CONCURRENCY = 1, asserted ≤ pool − ceiling. It also adds no per-row fallback at all: data errors are made impossible up front (U28 field caps plus a NUL strip), and a unique conflict gets an optimistic re-decide, then collapses to KEEP.
- FALSE as a step a session can run: '20 sequential calls from a browser on www.50pick.tz'. The ping is GROWTH-gated with step-up TOTP (rbac-guard.ts:120-142). Production has no QA admin, and Ali's login is never used (plan §0, the S9 note at :111-112). The measurement needs an owner decision or Ali at the keyboard (see ownerDecisionsNeeded #1).
- WRONG API: '<ProgressBar value={written} max={total}> with Batch 4 of 12 … beneath'. `label` is required (progress-bar.tsx:57-58). A line 'beneath' would be a second line under the built-in 'N of M · %' (88-100). The sentence has to be the caption + captionText pair (13-20), with each figure in its own .amount span.
- WRONG WORD: 'written'. A kept row is OD32's default and is counted skipped, so it is not written. The bar counts rows the server has DECIDED (the cursor, which equals count(outcome IS NOT NULL) by construction). The caption therefore reads 'Batch 4 of 12 · 1,847 of 5,912 rows done', and the done summary splits created, updated, skipped and failed.
- THE PRECEDENT MUST NOT BE COPIED: purgeAdvanceAction holds withLock around every batch (purge-actions.ts:183-195; locks.ts:158-159, 30 s timeout), and §5.5 (:1121) forbids a lock across an import. U32 claims each batch with a compare-and-swap on the run row inside a short per-batch transaction, never with an advisory lock.
- CONTRADICTION in U29's text: 'the run row carries the buckets, the written counters' (plan :2130-2131) breaks OD26, which forbids stored counters (:1011). U32 derives counts by groupBy over ContactImportRow.outcome. The cursor is a position, not a counter.
- CONTRADICTION in §3c: point 3 (:844-845) says U32's bar counts ROWS STAGED, but U32's own text counts rows written to the book. These are two phases. One pure driver and one bar primitive (import-loop.ts) serve both: U29/U30's staging upload reuses it, and U32 owns the commit phase. There must never be a second loop.
- ORDER CONFLICT: §10 puts U31·U32 at S15 and U33 at S16 (:2454-2455), yet U33 makes the basis a requirement before Apply enables (:2173). If U32 ships first, the server refuses with `no_basis` until U33 lands, so production import stays closed and U32 can be 🔵 at most. Swapping the order is cleaner (see splitRecommendation).
- WORDING CONFLICT: OD34 says 'never an eased animation' (:1032), but the shipped ProgressBar eases its width over 300 ms between two values (progress-bar.tsx:82). Ruling: allowed. It is OD38's shipped primitive with a reduced-motion branch, and it never passes the last value the server reported. What stays forbidden is a caption that counts up, or any value the server did not report.
- UNSTATED STATES: 'A server refusal stops the loop and shows the REASON' misses two failures that are not refusals. (a) A TOTP lapse is a NEXT_REDIRECT, which runAdminAction rethrows (run-admin-action.ts:28), so the page navigates away. (b) A deploy during the run turns the next call into a stale Server Action id (the comment block on next.config.ts deploymentId), which throws. Both must leave the run resumable, and (b) must say 'the platform was updated — reload to resume'.

**4. `src/lib/server/contacts/import-commit.ts`** (create)
